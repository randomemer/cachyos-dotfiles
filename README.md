# dotfiles

Config for a CachyOS / Hyprland 0.56 / DankMaterialShell (DMS) desktop.

```
manifest.txt   what is tracked, and how each path should be deployed
sync.sh        live config  ->  repo   (snapshot)
link.sh        repo         ->  live   (symlink)
config/…       mirrors ~/.config
```

## Symlink or copy?

**Symlink the things only you edit. Copy the things a program edits.**

The failure mode people worry about with symlinked dotfiles is real but specific:
a program that saves by writing a temp file and `rename()`-ing it into place will
replace your symlink with a regular file. The repo then silently stops receiving
changes, and you don't notice until the next `git status` shows nothing.

DMS was tested against exactly that on this machine — `~/.config/DankMaterialShell/settings.json`
was replaced with a symlink into a scratch repo, then written via
`dms ipc call settings set`:

| | result |
|---|---|
| config path after write | still a symlink |
| change landed in repo file | yes |
| repo file inode | changed (70 → 81 → 82) |

So DMS *does* rename-replace, but it resolves the symlink first and does the
replace at the **target** path. The link survives. That is the good outcome, and
it means symlinking is viable even for the DMS-managed files.

It is still a bet on DMS's current implementation, which is why the manifest
splits the two tiers. The `link` tier is safe by construction — nothing but you
writes those files. The `copy` tier works today and would need re-checking after
a DMS update. If you want it all symlinked anyway, `./link.sh --all` does that;
just re-run `git status` after a `dms setup` to confirm the links held.

One thing symlinks cannot protect you from: **`dms setup` regenerates
`dms/*.lua` wholesale.** That is a content overwrite, not a symlink problem —
it will happily write the regenerated file straight through your symlink and
into the repo. The upside is that you'd see it in `git diff` instead of losing
it. `dms/binds.lua` is the file at risk; per the DMS docs its contents can be
moved to `dms/binds-user.lua` verbatim, which `dms setup` does not touch.

### Recommended split

- **Symlink** — `hypr/hyprland.lua`, `hypr/config/*.lua`, alacritty, kitty,
  fish, uwsm/env, zed, micro, the frozen GTK/Qt theme files. Edits land in the
  repo with no further action.
- **Copy** — DMS settings, nwg-look/xsettingsd output, qt6ct, kdeglobals, btop.
  Run `./sync.sh` after you change them through their GUI.

```sh
./link.sh --dry-run    # preview
./link.sh              # symlink the `link` tier; originals -> .backup/<timestamp>/
./sync.sh              # snapshot the `copy` tier back into the repo
./link.sh --unlink     # put real files back everywhere
```

## Deliberately not tracked

**Auto-generated, machine-specific.** `hypr/dms/layout.lua` and
`hypr/dms/outputs.lua` both carry a `-- Auto-generated by DMS — do not edit
manually` header. `outputs.lua` additionally hardcodes this machine's DP-2
`2560x1440@179.877`, so it is actively wrong to carry to another machine. Both
are reproduced by `dms setup` plus the DMS Displays page.

**Regenerated by the tool that owns them.** `fish/fish_variables` (fish's own
universal-variable store), `hypr/hyprland.lua.dmsbackup1785640326` (a stray DMS
migration backup — safe to delete).

**Stock, zero customisation.** `~/.zshrc` and `~/.bashrc` are the untouched
CachyOS defaults (`.zshrc` is a single `source` line). Nothing to preserve; add
them the moment you customise either.

**Application data, not config.** vivaldi, mozilla, discord, Vencord,
obs-studio, vlc, r2modman, YouTube Music, dconf, go, menus, session, cachyos.
These are profiles and caches — large, churny, and some contain session tokens.

## Theme

Everything is Catppuccin Mocha with a mauve accent. kitty, alacritty, btop, Qt
and KDE use the official Catppuccin ports. DMS uses the Catppuccin theme from
its official registry (Mocha/Mauve); Hyprland borders use the `MOCHA_*`
colours in `hypr/config/colors.lua`. Catppuccin archived its GTK port, so
`gtk-*/catppuccin-mocha.css` are colour overrides on top of `adw-gtk3` instead.

Two parts only take effect with their packages installed: GTK3 needs
`adw-gtk-theme`, and Qt needs `qt6ct`.
